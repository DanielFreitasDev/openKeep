# Decisions

Key product and technical decisions, with rationale. Dated 2026-07.

## Product

1. **SPA + separate API in a monorepo** (user-confirmed). One app container serves both same-origin in production.
2. **Online-first with optimistic UI** (user-confirmed). Keep web itself is not a PWA and has no offline mode, so parity does not require offline. The data model stays offline-ready; installable PWA with cached reads ships in v1; mutation queueing shipped post-1.0 (see #22).
3. **i18n from day one** (user-confirmed): English base + full pt-BR. EN strings mirror Keep web verbatim.
4. **Native reminders — deliberate divergence.** Real Keep migrated reminders to Google Tasks (Oct 2025) and no longer sends its own notifications. A standalone clone has no Tasks, so we implement the *classic* Keep reminder UX: presets (Morning 8:00 / Afternoon 13:00 / Evening 18:00, configurable), custom date/time, recurrence, a Reminders view, and Web Push.
5. **Original artwork.** The 9 background illustrations are original work on the same themes; no Google assets anywhere. README carries a non-affiliation disclaimer. Working name "OpenKeep" avoids Google branding.
6. **JS masonry.** Native CSS masonry (`display: grid-lanes`) is Safari-only as of Jul 2026, so the grid uses a JS layout engine (absolute positioning + transforms). `grid-lanes` is a future progressive enhancement.
7. **Takeout importer in v1** — the killer adoption feature; the Takeout Keep JSON schema is documented and stable.

## Architecture

8. **Same-origin serving, no CORS.** The API and built SPA share one origin; cookies are `SameSite=Lax`; cross-site mutations are rejected via `Origin`/`Sec-Fetch-Site` checks. CORS is never registered.
9. **Per-user state lives on the membership row** (`note_members`): pin, archive, color, background, order — plus per-user labels and reminders. Shared content lives on `notes`/`note_items`. This is the single authz and display-state chokepoint.
10. **Field-level LWW, no OT/CRDT in v1.** Targeted PATCHes per field; item-level endpoints minimize the conflict surface for lists; the editor merges remote patches only into non-dirty fields. Documented limitation. **"Last writer" means the last *author*, not the last packet** (2026-08-02): writes to one note leave through a promise chain keyed by note id, because the outbox resumes paused mutations concurrently and the server keeps whichever lands last — an offline edit could arrive before an older save of the same field and be overwritten by it. Two people editing at once still resolve by arrival; one person's own edits no longer race each other. The same fix drops saves of content the server already has, which is where those older writes came from (an editor re-emits its content on a remote merge or a programmatic `setContent`, and each of those used to queue a PATCH nobody typed).
11. **Simple resync.** No oplog/cursor: on WS reconnect the client refetches active queries. WS is a best-effort accelerator over an online-first refetch baseline.
12. **Fractional ordering** (`fractional-indexing`): every move is a single-row write; tiebreak (position, id); stored `text COLLATE "C"`.
13. **uuidv7 primary keys** (native in PG 18); the client generates note ids so `?note=` URLs are stable instantly.
14. **`text` + CHECK instead of PG enums**; `timestamptz` everywhere; `updated_at` via Drizzle `$onUpdate` (no triggers).
15. **FTS**: custom text search config `openkeep` = `unaccent` filter + `simple` dict → accent-insensitive EN/PT word-prefix search with one GIN index, IMMUTABLE and legal in generated columns.
16. **Search UX is client-side** over the full corpus cache (instant, like Keep); the server FTS endpoint is the large-account/API escape hatch.
17. **In-process realtime registry** (`Map<userId, Set<socket>>`) behind a `publishToUsers()` abstraction → Postgres LISTEN/NOTIFY drop-in if multi-instance is ever needed.
18. **Undo snackbar = inverse mutation**, not cache rollback — survives server confirmation and other devices.
19. **Personal access tokens hand-rolled** (2026-07-28). Better Auth stays core-only (its API-key plugin is out per the plugin-CVE stance, #4 below), so PATs are a ~100-line module: `okp_` + 256-bit base64url secret, **sha256 at rest**, lookup by unique index on the hash (random 256-bit secrets make timing-safe comparison unnecessary), throttled `last_used_at`, optional expiry, 10/account. Bearer branch lives inside the existing `requireAuth`; token management endpoints reject PAT auth (a leaked token cannot mint tokens).
20. **MCP is an in-process client of our own REST** (2026-07-28). Tools never touch the DB: stdio talks HTTP with the PAT; the mounted `/api/mcp` builds an `OpenKeepClient` over `app.inject` carrying the request's PAT + `x-client-id: mcp:<tokenId>`. Validation, sanitize, authz-404, versioning and the WS fan-out therefore apply to AI traffic identically to browsers — and AI edits appear live in open tabs. The PAT is re-verified on every MCP request, so revocation is immediate.
21. **MCP SDK v2 mounting via `createMcpHandler` + web-fetch bridge** (2026-07-28). The `@modelcontextprotocol/fastify` adapter creates its *own* Fastify app (DNS-rebinding wrapper) rather than mounting into an existing one, so we bridge the SDK's web-standard handler onto our route ourselves: PAT gate → `handler.fetch(Request, {authInfo, parsedBody})` → stream the Response back. Host/Origin protection stays with the global cross-site guard (adapter-style host validation would break `trustProxy` deployments). SDK packages are spec-day releases pinned exact and excluded from `minimumReleaseAge`.

22. **Offline writes = outbox + draft mirror + visibility, not a sync engine** (2026-07-29). Three independent layers close the "wrote offline, reloaded, lost it" hole: (a) `create`/`patchContent`/`patchState` are keyed mutations whose lifecycle lives in `setMutationDefaults`, so a write paused while offline dehydrates to an IndexedDB outbox (persist-client; queries are NOT persisted — offline reads stay on the SW cache) and resumes after a reload; (b) a best-effort localStorage draft mirror (per-field timestamps, cleared on server ack, 7-day expiry) guarantees the content itself survives whatever the outbox can't — an errored-out mutation, a reload inside the persister's throttle — painted over the cached corpus at boot and re-sent once online; (c) an offline banner, failure toasts with Retry and a beforeunload guard replace silent failure. Replay semantics are the same field-level LWW as live edits (#10), with a wider window — accepted and documented. A replayed create dedupes via its client-generated id (409 conflict = already delivered). Checklist item CRUD keeps its per-item endpoints and rides the draft mirror only; composer images stay in-memory (see PARITY).

23. **Phones mirror the Keep *Android app*, not shrunken Keep web** (2026-07-29). Below `md` (768px) the shell swaps to the Keep-app layout, all CSS-breakpoint-driven so one DOM serves both: a single search-pill top bar (hamburger + hint + view toggle + avatar; the pill becomes the live input on `/search`), a fixed 2-up grid with a tighter gutter, a full-height drawer with a Settings entry (the mobile bar has no gear/refresh), an expandable create FAB (Image/List/Text) replacing the composer, and a full-screen editor — back arrow + pin/remind/archive up top, add/palette/format/⋮ bottom bar, menus as bottom sheets. Card hover toolbars disappear on phones; long-press (touch pointer, movement-cancelled) takes over selection. The FAB pre-creates the note (client id, outbox create) and opens it with `?new=true`; closing an untouched new note discards it Keep-style — trash→delete with bounded retries because delete-forever requires the trash hop and the create may not have landed, and the unmount-cleanup discard only fires when the URL no longer references the note (a cleanup while it still does is a StrictMode remount, not a close). A note born from a picked image never carries `new=true`, so the discard can't race the upload.

24. **Drawings are attachments: vector strokes + a rendered PNG** (2026-07-29). A drawing is an `attachments` row (`kind='drawing'`) whose `drawing_data` jsonb holds the editable stroke vectors (tool/color/size/flat point pairs, zod-capped) while the stored file is its PNG render cropped to the ink, Keep-style — so cards, editors, exports and Takeout keep treating it as a regular image, and "Make a copy" copies the vectors so copies stay editable. Re-saving replaces the render in place: a new `attachments.updated_at` rides the DTO so clients cache-bust the immutable file/thumb URLs (`?v=`), and `attachment.updated` joins the WS vocabulary. The full-screen editor (always light, like Keep's canvas) is route-driven via `?drawing=new|<attachmentId>` on the shell route; the note editor stands down while it is up (its modal focus trap would eat the canvas). From the composer/FAB the note is only created when ink is actually saved — no empty-note discard races — and input smoothing follows Keep's open-source ink_stroke_modeler idea (damped chase). The FAB from #23 gained a Drawing action (Image/Drawing/List/Text). The four extras deferred here landed in #35.

25. **PWA share target drains through the Cache API** (2026-07-30). The `share_target` manifest entry POSTs multipart to `/share`; the service worker reads the body, stores it under `share-target-v1` and answers 303 to a plain `GET /share` the router understands, because a POST navigation is not something a SPA route can consume. Cache over IndexedDB/postMessage: both sides already speak Cache and it stores `Blob` natively. The route is one-shot (reloading never creates a second note) and lives under `_shell`, so a share that arrives logged out survives the login round trip.

26. **The note vocabulary is markdown's, and markdown is hand-rolled both ways** (2026-07-30). v1.0 mirrored Keep web's May-2025 formatting surface exactly (H1/H2/B/I/U). Markdown phase A made the note *understand* that syntax as it is typed; phases B and C widen the surface itself to what markdown can express — H1–H6, strikethrough, inline code, fenced code with a language, blockquotes, rules, bullet/ordered lists and links (`NOTE_HTML_TAGS`, enforced by `sanitizeNoteHtml`: still zero styling attributes, links scheme-limited to http/https/mailto and hardened with `target=_blank rel="noopener noreferrer nofollow"`).

    Both directions are hand-rolled in `@openkeep/shared` rather than taken from `prosemirror-markdown` + `turndown`: the vocabulary is closed and enforced by the sanitizer, so a general parser would spend bundle weight producing nodes that get dropped, and a general serializer needs a DOM in Node. The parser is a CommonMark *subset* — no reference links, no setext headings (`---` under text stays a rule, the reading a notes app wants), no indented code blocks (four leading spaces are wrapped prose more often than code), no raw html beyond `<u>` (the one tag markdown cannot express and the note vocabulary has). Anything outside the subset survives as the characters the user typed: quietly losing pasted content is worse than pasting it verbatim.

    One engine serves every surface, which is the point: typing (TipTap input rules), pasting, `.md` import/export, the `markdown/` folder in the backup zip, version snapshots (stored as markdown, so a restore is lossless instead of flattening the note), list↔text conversion, and the MCP body surface agents read and write. Typing had to stop using StarterKit's own mark rules to get there — they anchor on `(?:^|\s)` while TipTap spells a hard break `%leaf%` (so `**bold**` never fired below the first line of a paragraph) and they guard only the opening delimiter (so `2 * 3 * 4` italicized). The replacements match the paste parser exactly, which is the invariant worth having: the same text typed, pasted and imported produces the same note.

27. **View-only sharing is a third level *inside* the chokepoint, not a second one beside it** (2026-07-31). `note_members.role` gains `viewer` next to the existing `owner`/`collaborator`, and `assertNoteAccess` gains a matching level: `member` (anyone on the note) < `editor` (owner or collaborator) < `owner`. Every route keeps its single call to the chokepoint (#9); the only work was classifying which level each one demands. `collaborator` deliberately keeps its name as the editor level — renaming it to `editor` would have rewritten stored rows, the `Collaborator` DTO, the realtime vocabulary, the MCP surface and both locales to say the same thing.

    The classification is the design: **shared content** — title, body, checklist items, attachments, note type, version restore — is `editor`; the note's existence — trash, restore, delete, merge, sharing itself — is `owner`; and everything the membership row owns per user (#9) — pin, archive, colour, background, board position, labels, reminder — stays at `member`. A viewer therefore organizes their own board exactly like anyone else, which falls straight out of the model rather than being a special case in it. `copy_note` is also `member`: a copy is a new note of the copier's own, and someone who can read the content can already retype it.

    A demotion has to reach an open editor, so the permission travels on its own event (`collaborator.role_changed`) carrying the affected user's role — the same event redraws the member list for everyone and flips that one person's note to read-only. The client mirrors the split in `lib/note-permissions.ts` (`canEditContent`), which is UI honesty, not enforcement: every call still lands on the chokepoint, and the 403 carries a distinct `note_read_only` code so a client can say *why* instead of "forbidden".

28. **Recording negotiates a container and the server transcodes nothing** (2026-07-31). Keep records only on Android; the browser can, so `MediaRecorder` feeds the audio attachment that already existed (`kind='audio'`, player, Takeout sniffer). Each engine records into its own container and refuses the others', so the client asks for the first candidate the browser admits — Opus in WebM (Chrome), Opus in Ogg (Firefox), AAC in MP4 (Safari) — and the take lands on `POST /api/notes/:id/audio`, which reuses the importer's `ingestAudio`: magic bytes decide the type as everywhere else, and the bytes are stored exactly as recorded. Re-encoding server-side would buy a media stack in exchange for fidelity, and the file is a recording, not a photo. The route is its own (not the images one) for the same reason it exists at all: audio carries a different byte cap, which the multipart parser has to be told per request, and skips the sharp pipeline entirely.

    A take under 400 ms never leaves the browser: the container declares its track only once audio flows (Chrome writes a bare 110-byte header below ~100 ms), so a stray tap produces a file the sniffer rightly refuses. Dropping it client-side turns a failed upload into a sentence.

    WebM is the one format the allowlist gained, and a signature was not enough for it: EBML says nothing about what it contains, so the same container would have made an audio route accept video. The rule reads the codec ids near the head instead — an audio codec must be declared and a video one must not — matching full names rather than the `A_`/`V_` prefix, because the window also covers compressed frames where two-byte needles occur by chance. Past the window it declines rather than guesses.

    A take counts as content the moment it exists, not when its upload acks. That matters because of #23: the FAB's Recording entry pre-creates an empty note marked `new`, exactly the state the editor discards on close — so the editor treats "recording running or take produced" as touched, and closing the note mid-recording keeps the take (the recorder stops on unmount, and the upload mutation is declared on `useMutation` so it outlives the editor that started it). The mirror case is the reason the note is created empty in the first place: a refused microphone leaves nothing behind.

29. **A note link is an anchor carrying the app's own deep link** (2026-07-31). `[[` inserts an ordinary `<a href="?note=<uuid>">Title</a>` — no custom node, no custom attribute, no new column. Everything the note already passes through knows what an anchor is, so the link survives the sanitizer, the markdown serializer (`[Title](?note=…)`), `.md` export and import, version snapshots, print and the MCP body surface without any of them learning a new shape. The href is relative because the modal opens over whatever route is showing (#13) and nothing inside a note should hard-code the instance's origin.

    The one place this costs something is the sanitizer, which until now refused every relative href: `?note=<uuid>` is admitted as an exact shape (`parseNoteLinkHref`), not as a general relaxation, and it is the only link that keeps neither `target=_blank` nor `rel` — a note link is not outbound, and a new tab for it would be a second copy of the app. The client completes that contract by intercepting the click in the capture phase, ahead of both the browser's navigation and TipTap's open-in-a-new-tab handler.

    The label is a copy of the title, not a live reference: renaming the target leaves the sentence that was written around it alone, which is both what `[label](href)` means in the file and the kinder behavior. Backlinks are the mirror and are computed client-side — a substring scan for the exact quoted href over the corpus the client already holds, the same bet instant search makes. Only bodies can carry them (checklist items are plain text), and if an account ever outgrows the scan the query moves to the server without the panel changing.

30. **A public link is one row, one address, and a projection of the note** (2026-07-31). `note_share_links` is keyed by `note_id`: a note has at most one public address, so sharing by link is a switch rather than a list, and issuing again overwrites the row — "regenerate" and "revoke" are the same guarantee, with never a second live address to keep track of. The 24-byte base64url token is stored in the clear, like the iCalendar feed's: the URL *is* the credential and has to stay copyable from any device, so a one-time-reveal hash would only break the thing it protects. Revoking is deleting the row, which every holder feels at once.

    The reader gets `zPublicNote`, not `FullNote`, and the difference is the whole privacy story: only *shared* content travels (type, title, body html, items, attachments, the owner's paper colour, the dates). Everything a membership row owns per user — labels, reminder, pin, archive, board position — stays behind, and no member's name or email appears anywhere, because the page is the note and not the account behind it. Trashing takes the link dark and restoring brings it back, since trashing is reversible and the link should be too; expiry (optional, 7/30 days) and an unknown token produce the same 404, so nothing on this surface is an oracle.

    Attachment bytes ride the same token — `/api/public/notes/:token/attachments/:id/:variant` — rather than a separately signed URL: the token already scopes the lookup to its own note, so an id borrowed from another note is a 404 by construction, and a second secret would have bought exactly that and a rotation problem. Everything anonymous here is rate limited, answers `X-Robots-Tag: noindex`, and is echoed by a `robots.txt` disallowing `/s/`; the SPA fallback stamps the same header on the page itself, since one HTML shell serves every route. The page lives outside `_shell` because there is no session to guard, no sidebar to draw and nothing to navigate to.

31. **A file attachment's bytes prove the container; its extension names the format inside** (2026-07-31). `kind='file'` joins image/audio/drawing so a note can carry a PDF, an office document, an archive or a text file — the thing self-hosters ask for that Keep has no answer to. The route is its own (`POST /api/notes/:id/files`) for the same reasons audio's is (#28): a different byte cap, which the multipart parser must be told per request, and no business in the sharp pipeline. Nothing is re-encoded and there is no thumbnail; the only thing added to the row is `filename`, required exactly when the kind is `file` (a DB check), because a document is the one attachment whose **name is content** — without it there is nothing to label a chip with and nothing to name a download.

    The allowlist is where the interesting constraint lives. Magic bytes alone cannot type these files: `.docx`, `.odt`, `.epub` and `.zip` are the same zip byte for byte, and `.doc`/`.xls` the same OLE2 compound file. So the signature decides the *family* and the extension picks among the entries of that family (`FILE_TYPES` in shared, read by the server to decide and by the client to build the picker's `accept`); an extension outside the table is a 415 whatever the bytes say. The browser's declared mime therefore still counts for nothing, exactly as with images and audio — a PDF renamed `.docx` is refused, and so is a zip renamed `.pdf`. Text is the one family with no signature to check, so there the proof is the content: it must decode as UTF-8 and carry no NUL or stray control bytes, which refuses a binary renamed `.txt` without pretending to guess a charset.

    **A download is always a download.** `Content-Disposition: attachment` is emitted only for `kind='file'`, on the private route and the public-token one alike, with the ASCII fallback plus the RFC 5987 form (`orçamento.pdf` has to survive). Images and audio stay inline because rendering in the page is what they are for, whereas opening an arbitrary file on our *own* origin hands the origin away — the same reasoning that keeps html and svg out of the allowlist rather than trusting a viewer to be careful. The API's own CSP (`default-src 'none'`) never covered these responses: it keys on content-type and files are not JSON.

    The chip sits with the link previews at the foot of the card and the editor, not in the image stack above the title: a document is something the note points at, not something it shows, and since the server forces the download the chip is a plain anchor and nothing more. Files ride the existing paths for free — the export zip already collected every attachment row, "Make a copy" copies the name along with the bytes, the public projection already shipped attachments, and `has:file` needed no SQL because the type filter was already generic over `attachments.kind` in both executors. The composer stays images-only: it holds files in memory before the note exists, which is the deferred "offline media" item, not this one.

32. **Who administers the instance is env, not a row; what they can change is a row** (2026-08-01). `ADMIN_EMAILS` (comma-separated, matched case-insensitively against the session's email) is the whole identity model for the admin panel, and Better Auth's `admin` plugin stays out by the plugin-CVE stance (#4/#19). An admin *flag* in the database would need a bootstrap answer for the empty instance ("who promotes the first one?"), would be one `UPDATE` away for anyone who reaches the database, and would drift from the deploy that actually owns the machine — whereas the env is already the thing the operator controls to run the server at all. Unset means nobody administers this instance: `GET /api/admin/me` answers `{admin:false}`, the menu entry never renders, and every other admin route is a 403 for everyone. The whole surface is session-only (`rejectPatAuth`), which also keeps it out of the MCP server, since MCP speaks to these same routes with a PAT (#20).

    What *is* stored is the one thing the panel changes at runtime: `instance_settings`, a single row (`id = 'singleton'`, enforced by a check) currently holding `signup_enabled`. A missing row means the defaults, so nothing has to seed it. The switch is enforced in `databaseHooks.user.create.before` — the one place a new account is born whichever door it came through, the sign-up form or a first OAuth login — rather than on the sign-up route, and it is read per attempt because Better Auth's own `disableSignUp` is decided at boot. An address in `ADMIN_EMAILS` is always let through it: the operator has to be able to create their own account on an instance they already closed.

    Deleting an account is the panel's one destructive act, and it leans on the schema instead of re-implementing it: every user-scoped table cascades from `user`, so the row going away *is* the deletion. What the database cannot do is the attachment files, collected before the rows go (a failure then leaves rows pointing at files, never the reverse) — the same order `deleteAllNotes` uses. Two guards frame it: the body carries a literal (`{"confirm":"delete-user"}`) and the dialog wants the address typed, because there is no trash behind this; and an account listed in `ADMIN_EMAILS` is refused outright, since deleting the row would leave a name that signs straight back in, and when it is your own it would lock you out of the panel that could undo it. One honest limit: sessions live in a signed cookie cache for five minutes (`session.cookieCache`), so a browser that was open when the account went keeps answering from it until it lapses — looking at an account with nothing left in it.

33. **A storage quota is charged to the note's owner, and the trash counts** (2026-08-01). `USER_STORAGE_QUOTA_MB` (unset = no ceiling) caps attachment bytes per account, enforced at every path that writes new bytes: the four upload routes, a drawing replacement (which pays only `new - old`), copy and merge — duplicated bytes are new bytes, and a copy loop would otherwise be the cheapest way around the cap. The bill goes to the **owner** of the note rather than to whoever uploaded, because enforcement has to use the same attribution as the accounting the admin panel has printed since #32; a per-uploader rule would let a shared note bill a stranger's allowance and leave the owner's reading of their own usage lying. Trashed notes count for the same reason: their files are on the volume until the purge takes them. The refusal is its own code (`storage_quota_exceeded`, 413) and not `payload_too_large`, because the two mean opposite things to a client — one says "send a smaller file", the other says "delete something" — and the client re-says only this one in the reader's language. Import is the one path that swallows it: a Takeout archive skips the media that will not fit exactly as it skips media it cannot decode, since failing a whole vault on the byte that crossed the line is the worse trade.

34. **Webhooks hang off the realtime chokepoint, and their vocabulary is smaller than it** (2026-08-01). Outgoing webhooks read the same stream the WebSocket does, through one optional sink on `Realtime.publishToUsers` (#17) — so a route that learns to publish learns to fire webhooks in the same line, and there is no second list of "events that also notify" to keep in step with forty call sites. What leaves the building, though, is deliberately not what travels inside: the socket talks to our own client, which ships with the server, while a webhook talks to somebody's n8n flow and every name is a promise to a stranger. So twenty internal events fold into seven note-level facts (`toWebhookEvent`) — an attachment upload, a checklist item and a paste are one "note.updated" — and the body is always `{event, noteId, note}` with the note read **at delivery time** through the ordinary per-user path, so a receiver never calls back and never learns the shape of our patch results. Two things follow from the hot path: the set of accounts with a live endpoint is held in memory (every keystroke's autosave publishes, and almost no instance has a webhook at all), and delivery is a pg-boss job with capped exponential backoff rather than an await inside the request. Signing is HMAC-SHA256 over `<timestamp>.<body>` — over the body alone it would be replayable forever — with the secret stored in the clear because we must reproduce it to sign, unlike a PAT's hash (#19). Reaching a private address is off unless the deploy says otherwise (`WEBHOOK_ALLOW_PRIVATE_TARGETS`): the SSRF guard built for link previews is right for a multi-user instance, and wrong for the homelab whose whole target list is on the LAN — that call belongs to whoever runs the machine, exactly like #32. The response body is dumped unread in both modes, so a webhook is never a way to fetch a page.

35. **The drawing extras are transforms over the same vectors, and a photo is a reference** (2026-08-03). The four things #24 deferred shipped as four deliveries over the storage that was already there. Zoom/pan is one transform applied on the way to the canvas, so its arithmetic lives apart (`lib/drawing-view.ts`) and is unit-tested: the fit scale is the zoom **floor** (going below it only adds margins to a page you can already see whole) and every pan is clamped so the paper cannot be parked half off-screen; the view re-fits itself on resize only until the person takes it over. The lasso keeps a stroke only if the loop encloses **all** of it — a half-crossed neighbour staying put is what lets a loose circle mean one word — and moving is a single undo op holding the stroke references plus a delta, which is also why any undo/redo drops the selection: history rearranges the very strokes it points at. Auto-extend needed a frame loop rather than an event handler, because a pen parked against the bottom edge sends no pointer events at all; growing deliberately clears the "fitted" flag, since re-fitting a page that just got taller would shrink the ink mid-stroke. Drawing over a photo could not bake the picture into `drawing_data` (a base64 photo would blow the 1 MB cap), so it stores a reference: `photoAttachmentId`, an optional field rather than a `version: 2`, pointing at an image attachment of the same note. Two consequences are the whole design: the DTO surfaces the link so the client can hide the bare photo from the note's picture stack (one `selectImageStack`, honoured by cards, editor, print and the public page) without fetching every drawing's vectors, and "Make a copy" remaps the id to the copy's own photo — otherwise deleting the original note would take the copy's background with it. The photo stays attached because it is what keeps the drawing editable, and it reappears if the drawing is deleted. The composite is stored as **JPEG** (the renderer picks the format, the server accepts both): a photograph re-encoded as PNG is megabytes of somebody's quota for pixels that were never lossless.

36. **The title and the items get a snapshot ring, not a second command history** (2026-08-03). TipTap's history covers the body and nothing else, so Ctrl+Z in the title used to hit the browser's per-field undo (and in a checklist row, whose textarea is controlled, nothing at all). The fix is a ring of whole snapshots per editing session (`lib/field-history.ts`, 100 steps), not inverse operations: the item algebra is already eight verbs — add, split, merge, check-with-cascade, indent, reorder, uncheck-all, delete-checked — and inverting each is eight chances to be subtly wrong, where restoring "how it read" is one. Three things fall out of that choice. **Steps address rows by local key, never by server id**, because undoing a deletion means *creating* a row, and every later step has to keep pointing at it — restore matches by key, reuses whatever id the row has now, and creates one where there is none. **A step is recorded from an effect on the committed rows, not from the op**, which is what makes Enter (a text change plus a row) one step and leaves the `setRows` nobody asked for — a collaborator merging in, an id landing from the server, a restore — out of the history entirely. And **undo/redo push the note as it reads at that moment**, not the snapshot the last step left: a collaborator's edit can arrive between two steps without being one, and pushing what is actually on screen onto the opposite stack is what stops a later redo from resurrecting a value they had already replaced. Coalescing is per field with ProseMirror's own half-second window, so a typed word is one step and a structural change never joins one. The two histories share the shortcuts by surface: a keystroke belongs to the field it was typed in (the body keeps its own until it runs dry), while the toolbar buttons follow whichever surface was edited last and fall back to the other. A type conversion resets the ring — the server has just rewritten the content the steps describe.

37. **A table is what a `|---|` row can say, and nothing else** (2026-08-03). Tables were the last markdown block outside the note vocabulary (#26), and the shape of the feature came from asking what the *serializer* can carry rather than what the editor could offer. GFM has no syntax for a merged cell, a column width or — in a vocabulary with no styling attributes — an alignment, so `NOTE_HTML_TAGS` gains `table/thead/tbody/tr/th/td` and not one attribute, and the TipTap cells are extended to match: `colspan`/`rowspan` stay in the schema because prosemirror-tables reads them to build its column map, but they are pinned at 1 on the way in and never rendered, so a merged cell pasted from a web page arrives as plain cells instead of as a merge the next save would silently undo. Alignment colons parse and are dropped for the same reason — reading `:-:` and then losing it at the first save is worse than never showing it. Two invariants keep that honest. **Every table is rectangular**: un-merging a pasted cell leaves the row short and html written straight through the API can be ragged from the start, so a plugin runs prosemirror-tables' `fixTables` on every transaction, and the parser pads and truncates each row to the header's width the way GFM does. And **the first row is the header** whether or not it is spelled with `th`, because markdown has no headerless table and the editor always makes one. The parser needs a pipe on *both* lines to see a table at all — without that, `a` over `---` (a rule here, a setext heading in CommonMark) would become a one-column table, and `- a | b` over `- | -` would stop being the two-item list it looks like. Cells hold inline content only, and everything below them flattens: a break inside a cell becomes a space in the markdown and in the plain-text projection, where a row is one line with `|` between the columns so FTS, the `.txt` export and the card snippet still read it as a row. On screen the grid is `table-layout: fixed` at full width in cards, editor, public link and print — a long cell wraps and costs a line, where a scrolling one would cost the column and put a horizontal scrollbar on a sticky note.

38. **The one Better Auth plugin we take, and the four things bought to justify it** (2026-08-04). The hosted assistants are the reason: ChatGPT's connector accepts OAuth 2.1 or no auth and will not present a fixed secret at all, and Claude's static-header option is a gradual beta — so "PATs only" (#19) meant the two clients most people actually use could not reach `/api/mcp`. That makes OpenKeep an authorization server, and the choice was to hand-roll one or take `better-auth/plugins/mcp`, which reverses the core-only stance the api-key (#19) and admin (#32) plugins were kept out by. The plugin won on the argument that made those two lose: an API key is a hash and a lookup, an admin flag is a string compare, and writing either is smaller than auditing a dependency — whereas an OAuth AS is discovery, registration, PKCE, consent, refresh and revocation, where *our* bugs are likelier than the library's. What the stance buys instead is spent on the parts the plugin leaves open. **Registration is unauthenticated** (the discovery flow requires it), so a stranger can mint a client and craft an authorize link; the plugin only shows a consent screen when the *client* asks for one, which is precisely backwards, so the Fastify bridge forces `prompt=consent` on every authorization and the screen leads with "OpenKeep has not verified this app" over the callback host — the one claim a registration cannot fake. **PKCE is mandatory**, not merely offered, because with open registration it is the only thing binding a code to its requester. **Tokens are opaque rows, not JWTs**, so disconnecting a connector deletes the grant *and* its live tokens and access stops within the request rather than at the hour mark — the same immediate-revocation property #19 chose for PATs. And the OAuth POSTs get a **60/min budget separate from the 10/min credential limit**: none of them takes a password, one connect already costs three of them, and a shared egress IP would otherwise turn the anti-guessing limit into connectors that mysteriously stop working. The grant itself is all-or-nothing (OIDC's scopes, none of which narrows anything), so an OAuth token is exactly a PAT in reach — which is why `rejectPatAuth` now turns away both, keeping the admin panel and token management session-only as #32 requires.
